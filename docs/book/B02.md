# B02 · Immutable data

**Denotes.** A value never changes: an update produces a NEW value and the old one stays exactly as it was. The measured #3 violated concept in the fleet's Kotlin mains.

## 1 · The aha

A rebindable slot is a hidden channel: any line that writes it reaches any line that reads it, and neither mentions the other. A value that cannot change turns that channel off — what a function sees is what it gets, every time, forever.

## 2 · What it denotes

In Haskell nothing rebinds: `let x = 1` is one binding forever, and an update builds a new value that shares structure with the old one — so the new value costs almost nothing and the old one stays valid. The Okasaki result: for everyday shapes the cost of immutability is a myth; only huge hot buffers pay real copy prices, and those belong at an edge.

## 3 · In your languages

**Kotlin.** `val` is the binding law: main sources bind `val` only, and a new value replaces the old — `rows.fold(0) { acc, r -> acc + r.n }` carries the accumulator, `state.copy(open = true)` produces the update. `var` lives in test sources (fixtures, `lateinit`) and nowhere else; the registered law-hook denies it in mains since U13. Full row: `kotlin-kb/notes/canon-map.md`, `immutable-data`.

**Nushell.** The language agrees with you: a closure cannot touch your `mut` slot, so the accumulator dies anyway and `reduce --fold` carries the intermediates instead; `$cfg | update port 2` answers a new record while `$cfg` stays untouched. `mut` survives at script edges only. Full row: `nushell-kb/notes/canon-map.md`.
