# H15 · Profunctor: the common shape of processes and data access

**Denotes.** A functor from the opposite of one category times another into `Set`: contravariant in what it receives (H14), covariant in what it produces (H02) — a proof-relevant relation between objects.

## 1 · The aha

One shape under three hats you already own: the plain function (consume `a`, produce `b`), any process that takes one type and emits another, and the data-accessors of H19 — all lift a pair of functions, one against the flow, one with it: `dimap`.

## 2 · What it denotes

A functor `p : C^op × D → Set`: for `f : c → a` and `g : b → d` you get `p a b → p c d` — "if we have a proof that `a` is related to `b`, then we get the proof that `c` is related to `d`, as long as there is a morphism from `c` to `a` and another from `b` to `d"`.

Composition runs through an intermediary, `(q ∘ p) a b = ∫^c p c a × q b c`, with the hom-functor as unit, and both laws "hold only up to natural isomorphism".

In Haskell: `class Profunctor p where dimap :: (a -> b) -> (c -> d) -> p b c -> p a d`, with `lmap` and `rmap` as its halves, and the function instance `dimap ab cd bc = cd . bc . ab`.

The approximation: "to first approximation, Haskell types are sets", and the Typeclassopedia has no section on it. The trap: reading `p a b` as a function `a → b` — for `(->)` the first function is pre-composed, so `p b c -> p a c` needs an `a -> b`, not a `b -> a`. Full theory: `theory-kb/notes/category-theory/profunctor.md`.
