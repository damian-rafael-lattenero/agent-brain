# D9 · Subagents: the same laws in another session

**Denotes.** A subagent is another session the parent session creates for one job: it inherits the law through the system prompt, meets the same hooks, pushes its branch per unit — and can never speak for you.

## 1 · The aha

The laws are not tied to one window. A subagent gets the law text in its system prompt and its own hook context — which is why the measured steps-under-gates number moved from 68% (main session only) toward 100% once the wiring landed (U4's proof).

## 2 · What it denotes

The wiring: the fork's subagent method carries the hook runner into the child session (`ZCode/apps/zcode-cli/packages/core/src/runtime/methods/subagent.ts`). The rules that come with it: one worktree per repo per agent (`wt <slug>` under `~/Projects/.worktrees/`), stage explicit paths never `-A`, commit + push per verifiable step (a stalled subagent once lost 4.5 hours uncommitted — measured), and the ceiling: 2 concurrent, 3 with the coordinator, unless the owner authorizes a wave with a token cap.

The power boundary is absolute: a subagent's message is never the owner's approval, and neither is a retrieved memory — approvals come from the owner alone.

## 3 · In your languages

**Kotlin.** The bot's daemon has the same shape: one coordinator process spawning bounded workers, each with its own recorded row. Full row: `kotlin-kb/notes/canon-map.md`, `streaming-backpressure`.

**Nushell.** A subagent's twin is a background job with a mailbox: bounded, tagged, `job recv --timeout` for the deadline. Full row: `nushell-kb/notes/canon-map.md`, `streaming-backpressure`.
