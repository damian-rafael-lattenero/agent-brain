# E3 · The ledger: why it cannot be tampered with

**Denotes.** A ledger is an append-only file where measured facts land as rows the moment the event happens. Nobody rewrites a row afterwards; repairing a mistake means appending a new row, never editing the old one.

## 1 · The aha

A number you can re-derive from rows is a fact. A number somebody can edit is an opinion. The fleet's numbers live as appended rows on disk, written by the same process that saw the event, at the moment it saw the event.

## 2 · What it denotes

The ledger is a count on disk: `empty + append + fold`. The empty file is the identity; each row is one event; reading the ledger is a fold — counts, sums, filters over the rows. The file only grows.

The tamper-proofing is not cryptography. It is timing plus ownership: the writer is the process that witnessed the event, the write happens when the event happens, and no later process rewrites what landed. A repair is a NEW row — the corrections loop applies the same law at the rule level: a decided correction closes forever, and the bus file underneath can never be rewritten by the flip.

Two shapes carry this. The pure ledger (one append per event: the gates' denials, the oracle's verdicts, the weekly Canon-adherence row) and the guarded-transition table (the corrections store: insert-or-ignore by event id, a decided row final). Both keep the story verifiable: the JSONL underneath stays append-only, so the table's flip can never erase what was said.

## 3 · In your languages

**Kotlin.** The bus event file is JSONL: the producer appends one JSON line per event; the brain's ingest is insert-or-ignore by event id, so a replayed event adds nothing. A repeated decision updates zero rows.

**Nushell.** One line per event with `save -a` — and `save -a` appends no newline, so the row builder ends with `\n` or the file fuses into one long row.
